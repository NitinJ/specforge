# Interactive components

## TL;DR

<!-- sf:box class="panel" -->

Ship a second component collection for blocks that respond to a reader. It is generated by the same pipeline as the 39 static components and shown at `/components-interactive`.

Behaviour arrives in two ways. A disclosure needs no script at all and is stamped as CSS like every component today. Everything else is authored as complete static content and reduced by a script the review layer lazy-loads from `/public/interactive.js`, the way it already loads mermaid and Prism. No spec file ever gains a `<script>`.

First cut is four components: **disclosure**, **tabs**, **sortable table**, **copy button**. Five stages.

## 1 · Overview

The library is 39 components across 7 families, and every one of them is inert. A spec presents by layout, colour and type only: a reader gets one arrangement of the document and no way to ask it for a different one.

Three shapes recur in specs and none of them are servable today. A long table of measurements that matters to two readers out of ten still costs every reader the scroll. The same configuration written three ways, one per environment, is three blocks where a reader needs one. A comparison table sorted by the column the author cared about cannot be re-sorted by the column the reader cares about.

Each of those is a presentation problem with a known solution, and every major document product ships at least one of them. The question this spec answers is not whether to build them; it is how behaviour reaches a document that must also render from `file://` with no network, survive publication to a stranger, and export to markdown.

- **39** static components today
- **8,045** bytes stamped per spec
- **0** interactive components
- **4** proposed in the first cut

components/index.mjs and templates/components.css at commit 28b2a06, 2026-08-18

## 2 · Survey

What document products actually ship, and what Material offers that a document could use. Sources retrieved 2026-08-18.

### 2\.1 · Document products

| Capability | Notion | Confluence | Google Docs |
| --- | --- | --- | --- |
| **Disclosure** (collapse a block) | Toggle list, toggle heading | Expand macro | Collapsible headings (pageless) |
| **Tabs** (alternatives in one place) | none | Marketplace only | document-level only |
| **Sortable / filterable table** | Database views | Table Filter (Marketplace) | none |
| **Stateful chip** (a value a reader sets) | Select property | Status macro (author-set) | Dropdown smart chip |
| **Generated navigation** | Table of contents block | Table of Contents, Children Display | Outline pane |
| **Transclusion** (one source, many pages) | Synced block | Excerpt / Excerpt Include | none |

<!-- sf:callout variant="note" -->

> **The disclosure is the only one all three ship natively.** Notion calls it a toggle list, Confluence an Expand macro, Google Docs a collapsible heading. Three products that share almost no vocabulary converged on this one block.
>
> **Tabs are shipped natively by none of them.** Atlassian's own macro catalogue points readers at the Marketplace for tabs rather than to a core macro. Google Docs' tabs are document-level navigation, not a block inside the prose. That is evidence about difficulty and about editing models, not about reader value: the Marketplace app exists because the demand does.

### 2\.2 · Material

Material 3 lists over 30 components. Most are application chrome and have no meaning in a document that is read rather than operated: buttons, floating action buttons, dialogs, snackbars, navigation bars, drawers and rails, sliders, switches, text fields, date and time pickers, search fields. A document has no state to submit and no destination to navigate to.

Six are candidates because they arrange content rather than collect input:

| Material component | What it does | Use in a spec | Verdict |
| --- | --- | --- | --- |
| Expansion panel (M2) / disclosure | Collapses a block behind a summary line | Detail a reader needs sometimes | first cut |
| Tabs | One of several peer views at a time | The same thing per platform or environment | first cut |
| Segmented button | Switch views, 2 to 5 options | Duplicates tabs at a spec's width | rejected |
| Chips (filter) | Narrows a collection | Filtering a long table | deferred |
| Carousel | Items scrolled on and off screen | A spec is scrolled vertically already | rejected |
| Lists (with trailing controls) | Rows with an action each | Covered by tables and checklists | rejected |

### 2\.3 · What the survey settles

- The disclosure carries the most evidence of the four: 3 of 3 products ship it natively, and it needs no script.
- Tabs carry real value and real risk. No document product ships them natively, so there is no convention to copy and the failure mode is known: content a reader never finds because it was behind a tab they did not click.
- Sorting belongs to tables, not to a component. Notion and the most-used Confluence marketplace category both attach it to the table rather than introducing a new block.
- Everything Material offers beyond these is input collection, and a spec collects nothing.

## 3 · Goals & non-goals

<!-- sf:section id="goals" -->

#### Goals

- An agent picks an interactive component the same way it picks a static one: by reading a rule in `references/spec-components.md` and writing the markup the entry shows.
- A spec carrying interactive components is complete with no JavaScript. Not degraded to a warning, not degraded to a first tab: complete, and longer.
- Behaviour is fixed in one place. A defect in a component's script is fixed once and every spec already written is fixed, with no re-stamp and no migration.
- Every interactive component has a defined markdown form, so export stays lossless.
- The showcase at `/components-interactive` demonstrates each component live, the way `/components` does.

#### Non-goals

- Reader state that persists. Nothing a reader clicks is written to the store or to the spec.
- Anything that collects input. No forms, no fields, no submission.
- A second build pipeline. See [D1](#decisions).
- Retrofitting the 133 specs already in the store.
- Editing. These components are authored by an agent writing HTML, not by a person clicking.

## 4 · Design

### 4\.1 · Summary

A component's layer is decided by one question: **what does a reader lose when no script runs?** The answer sorts every candidate into three groups, and only two of them ship.

| Layer | Behaviour comes from | Without script | Ships as |
| --- | --- | --- | --- |
| **Native** | The HTML element itself (`<details>`) | Fully interactive | Stamped CSS, exactly like today |
| **Enhanced** | `/public/interactive.js`, lazy-loaded | Complete and longer | Stamped CSS plus a served script |
| **Refused** | Script only | Content missing | not built |

The third row is the constraint doing the work. A component whose content exists only after a script runs cannot be written, because a spec must render from `file://` with no network, and because the markdown export reads the file rather than a browser.

### 4\.2 · The enhancement contract

An enhanced component is authored as complete static content. The script does not build the component; it *reduces* one that is already there. Tabs are authored as a run of panels, all visible; the script hides all but one and adds the strip that switches between them.

One rule makes that safe, and it is the rule the whole layer rests on:

<!-- sf:callout variant="constraint" -->

> Stamped CSS MUST NOT hide content. Every rule that hides is written under `[data-sf-live]`, an attribute only the script sets. The stylesheet is stamped into the file; the attribute is not. A document that never runs the script therefore never hides anything.

Written the obvious way instead, `.sf-tabs > .sf-tab { display:none }` would sit in the stamped block of every spec, and a reader opening the file from disk would lose every panel but the first, permanently and silently.

![Authored content is complete; the served page adds an attribute and a script that reduce it; the file on disk keeps everything](2026-08-18-interactive-components-spec.assets/design-1.svg)

<!-- sf:svg id="design-1" -->

### 4\.3 · Where the script lives

In `server/public/interactive.js`, lazy-loaded by `review.js` when the document contains a component that needs it. That is not a new mechanism: `review.js` already loads `/public/prism.js` and `/public/mermaid.js` exactly this way, on demand, with a timeout.

| Option | Pros | Cons | Verdict |
| --- | --- | --- | --- |
| **Served by the review layer**<br>one copy at /public/ | Fixed once, every spec fixed. No spec file contains executable code. Matches the existing mermaid and Prism path. Works on publications, which serve the same assets. | A spec opened from `file://` is static. | chosen The cost is bounded by the enhancement contract: static means complete, not broken. |
| **Stamped into every spec**<br>like components.css | Self-contained. Interactive from disk. | Every JS fix means re-stamping 133 specs, and the stamp is hash-guarded so a hand-edited spec refuses the re-stamp. Adds ~8 KB of script to every spec whether it uses one or none. Puts executable code inside a file that is published to strangers and imported from untrusted markdown. | rejected |
| **Inline per component**<br>a script tag beside each block | Only pays for what is used. | Every objection above, plus the same script duplicated once per instance, plus an agent authoring executable code by hand. | rejected |

<!-- sf:callout variant="decision" -->

> Keeping `<script>` out of spec files is a security property, not a preference. **Criterion:** specs are imported from untrusted markdown and published to readers who are not the author. **Not taken:** stamping, which would make the library the first channel that writes executable code into a document.

### 4\.4 · One registry, two documents

The 39 components today are defined once in `components/` and read by five consumers: the stamped stylesheet, the lint registry, the lint's commentability allow-list, the markdown exporter's notice types, and the library document. Interactive components need all five.

They get them by adding one field to the component shape rather than by adding a second directory with a second build:

components/index.mjs

```
layer: 'static' | 'interactive'   // default 'static'
needs: 'none' | 'script'          // interactive only; drives the lazy load
```

`specforge components build` then emits two documents from one pass: `/components` filtered to `layer === 'static'` and `/components-interactive` to the rest. Both are reserved store ids, served only at their own route, as `specforge-components` is today.

<!-- sf:callout variant="risk" -->

> A parallel `components-interactive/` directory with its own builder is the obvious shape and the wrong one. **Trigger:** two pipelines emitting into the same stamped block. **Consequence:** the drift is measured, not hypothetical. Commit `28b2a06` removed six independent copies of the table rules that had accumulated across five shells and the library page, one of which had already silently disabled the heading family.

### 4\.5 · What the change touches

| Surface | Today | Change |
| --- | --- | --- |
| `components/index.mjs` | 39 components, 7 families, no layer | Add `layer` and `needs`; add the interactive family |
| `lib/components-build.mjs` | Emits one stylesheet, five shells, one doc | Emits a second doc; stylesheet gains the interactive rules |
| `lib/components-doc.mjs` | Builds `specforge-components` | Parameterised by layer, builds both |
| `server/daemon.mjs` | Serves `/components` | Serves `/components-interactive` |
| `server/public/review.js` | Lazy-loads prism and mermaid | Lazy-loads `interactive.js` on the same pattern |
| `server/public/interactive.js` | new | Sets `data-sf-live`, wires each component |
| `lib/html-to-md.mjs` | Handles callouts, stats, plans, code, tables | One static form per interactive component |
| `lib/lint-spec.mjs` | Reads the registry | No change; the registry grows |
| Contents rail (`review.js`) | Lists h2 to h4 | Must open a collapsed block before scrolling to a heading inside it |
| Comment anchoring | Anchors to any block component | Must open a collapsed block that holds the anchored text |

### 4\.6 · How an agent reaches for one

Unchanged from the static library. `references/spec-components.md` is regenerated by the same build and gains the interactive entries, each with its rule, its required markup and its contract. The authoring skill already sends an agent there. A component is chosen by what the block asserts, never by how it should behave.

<!-- sf:callout variant="example" -->

> `disclosure`: detail a reader needs on a second pass and not on the first. **Requires:** a summary that states what is inside, so the block can be skipped without opening it. **Never:** content the reader must see to follow the argument.

Buttons, floating action buttons, dialogs, snackbars, navigation bars, drawers, rails, sliders, switches, text fields, date and time pickers, search fields, carousels. ## 6 · Invariants

What must hold after this ships. Each is stated so a test can fail on it.

| # | Invariant | Fails when |
| --- | --- | --- |
| **I1** | No rule in the stamped stylesheet hides content except under `[data-sf-live]`. | A spec opened from disk is missing a panel. |
| **I2** | The library never writes `<script>` into a spec file. | An imported or published spec carries executable code. |
| **I3** | Every interactive component has a markdown form, and no content is dropped by export. | A round trip loses a tab panel. |
| **I4** | An interactive block is a comment target like any other block component. | A reviewer cannot comment on a tabbed block. |
| **I5** | Navigating to an anchor inside a collapsed block opens it first. | A contents-rail link scrolls to nothing. |
| **I6** | Printing expands everything. | A printed spec is shorter than the document. |
| **I7** | The stamped stylesheet stays the single definition. Nothing that carries it redefines a selector inside it. | The test added in `28b2a06` fails. |

## 7 · Decisions

| # | Decision | Choice | Rationale |
| --- | --- | --- | --- |
| D1 | A second collection, or a second pipeline? | A second *document*, from one registry and one build | Two builders emitting into one stamped block is how the six duplicate table definitions happened. A `layer` field gives a separate collection without a separate pipeline. |
| D2 | Where does the script live? | `/public/interactive.js`, lazy-loaded by the review layer | One copy to fix. No executable code in a file that is published and imported. Identical to the existing mermaid and Prism path. |
| D3 | What happens with no script? | The document is complete and longer | A spec must render from `file://`. Progressive enhancement is what makes the served copy an improvement rather than the only working copy. |
| D4 | Accordion: `<details>` or a custom block? | `<details>` and `<summary>` | Zero script, native keyboard and screen-reader behaviour, native find-in-page expansion, and markdown export for free. A custom accordion buys styling freedom and pays for it in all four. |
| D5 | Is sorting a component or a variant? | A variant on `table` | Notion and Confluence both attach ordering to the table rather than introducing a block. A second table component would split the vocabulary. |
| D6 | Are headings inside a disclosure in the contents rail? | No | The same rule that keeps `h5` out. A disclosure holds second-pass detail, and an outline that lists second-pass detail is not an outline. Resolves Q1. |
| D7 | Where does tab selection live? | The URL fragment, via `replaceState` | No stored reader state, survives a reload, and makes a panel deep-linkable so a comment can anchor inside a hidden one. GOV.UK ships the fragment. The back button does not step through selections, which is the price of not scrolling on every switch. Resolves Q2. |
| D8 | What does a tab label export as? | A bold line | A tab label is an `h5` by the library's own definition. A heading would inject one false outline entry per panel into the exported markdown. Resolves Q3. |
| D9 | Does the lint police disclosure size? | It warns on a contained `h2` or `h3`, advisory only | Names the actual failure without inventing a threshold there is no measurement to set. Resolves Q4. |

## 8 · Open questions

All four resolved with the conventional answer rather than a novel one. Each is reversible and none blocks a later change of mind.

- [x] **Q1 — resolved** A heading inside a collapsed disclosure is **not** listed in the contents rail. The library already decided this shape once: `h5` is absent from the rail because a rail that lists every label stops being an outline. A disclosure holds detail a reader needs on a second pass, so its headings are the same kind of thing. I5 still holds for a comment or a link that targets text inside one.
- [x] **Q2 — resolved** Tab selection lives in the **URL fragment**, as GOV.UK's tabs do. Nothing is written to the store or to local storage, so the non-goal holds; a reload lands on the same panel; and a panel becomes deep-linkable, which I5 needs anyway to anchor a comment inside a hidden one. Written with `replaceState`, so the **back button does not step through selections**: `pushState` would give that and fill the history with an entry per click, and assigning `location.hash` would scroll the panel to the top of the viewport on every switch.
- [x] **Q3 — resolved** A tab label exports as a **bold line, not a heading**. A tab label is an `h5` by the library's own definition: a label over a run of prose, not a division of the document. Exporting it as `h3` would put four panels into the outline of the exported markdown as if they were four sections.
- [x] **Q4 — resolved** The lint warns, advisory only, when a disclosure contains an `h2` or an `h3`. That is the failure the component rule names (the argument hidden behind a summary) stated as a check that needs no threshold. The proportion-of-section rule is dropped: it needs a number, and there is no measurement to set one from.

## 11 · Runtime

Filled during implementation. The runtime record CLAUDE.md asks for, in one place.

Shipped 2026-08-18 in PRs #206, #209, #210, #211, #212 and #214, merged to `better-ui`. 43 components, 4 of them interactive. Unit suite 0 failures, e2e 125/125.

#### Design decisions (implementation time)

- **A component's `kind` decides more than its markup.** `disclosure` is registered as a `class` although an author writes a tag too, because `kind` drives the lint's allow-list and the commentability list. As an element it would be in neither: the lint would reject the class the library tells authors to write, and no comment could anchor to the block, breaking I4.
- **Semantic families, not an "interactive" family.** The layer decides which document a component appears in; the family decides how it is grouped inside that document. Keeping them independent gives the interactive page three meaningful groups (Structure, Data, Code) rather than one bucket named after the thing they already have in common.
- **Reserved entries carry their own route.** Three places had each hardcoded `/components`: the daemon that routes it, the client that prints its url, and the spec route that refuses it. One map now, so a third reserved document is one entry.
- **An unrecognised `layer` or `needs` throws.** The default is for a component that says nothing; one that says `interactve` has made a claim, and reading it as `static` would file it in the wrong document and report nothing.

#### Deviations

- **D7 overstated what the URL fragment buys.** The spec claimed the back button steps between tab selections. `replaceState` creates no history entries, so it never did. The claim was corrected rather than the behaviour: `pushState` would add an entry per click and assigning `location.hash` would scroll on every switch.
- **No Stage 0.** The impl shell asks for a test-setup stage; the existing jsdom and Playwright harnesses already covered every surface, so the plan opened at Stage 1.
- **Q4's proportion rule was dropped, not implemented.** "A disclosure holding more than some fraction of a section" needs a threshold there is no measurement to set. The lint reports a contained `h2`/`h3` instead, which is the same failure stated concretely.

#### Tradeoffs

- **The copy control trims nothing.** Two attempts to strip "the markup's" trailing whitespace each lost real content: `\s+$` took the two trailing spaces that are a hard line break, `\n+$` took a deliberate final blank line. Nothing in the page can tell an artifact of the markup from the author's text, so the control hands over exactly what the block contains.
- **A tab summary stays HTML.** Converting a disclosure's summary to markdown put literal backticks on the page, because `<details>` opens an HTML block where markdown is not parsed. Three rounds of repair chased the conversion before it was removed. A raw HTML block renders HTML, so the author's markup was already correct.
- **A sortable header that already holds a control is left unsorted.** Wrapping it would nest interactive content: invalid, unreachable by keyboard, and every press of the inner control would also sort. One unsorted column is the cheaper failure.
- **Printing expands disclosures from the review layer, not from CSS alone.** The stamped `::details-content` rule is all a spec opened from `file://` can do and is honoured by newer engines only, so I6 holds fully only where the layer is present.

#### What review caught

16 findings across four rounds, every one real. The six worth recording, because each is a class of mistake rather than a typo.

| Defect | Why it had no symptom |
| --- | --- |
| A closed disclosure exported as open | `\bopen\b` matched the word inside a class list such as `disclosure open-question`. The export silently said the opposite of the document. |
| A nested disclosure evaded the depth lint | A non-greedy `<details>…</details>` pair stops at the first closing tag, so it read the inner block and missed the outer one. |
| A third contents-rail path still listed hidden headings | Two of the three collection paths learned to skip disclosures. The fallback for documents with fewer than three sections did not. |
| A refused clipboard skipped its own fallback | The textarea path ran only when the API was absent, never when it rejected, so a page that could copy said "Press ⌘C". |
| A malformed URL fragment aborted tab setup | `decodeURIComponent` threw inside the group loop, leaving every tab group below it unbuilt. |
| `role="button"` on a `<th>` | It overrides the native `columnheader` role, which is what makes `aria-sort` mean anything. The component announced a sort state on an element that had stopped being the thing the state is about. |
