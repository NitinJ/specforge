SpecForge markdown interop

Spec · 2026-08-14 · status: draft · owner: nitin

TL;DR

Two new paths in the SpecForge plugin. specforge export-md <id> renders a store spec as a GFM markdown file plus a sidecar assets directory holding its SVG diagrams. specforge import-md <file> converts any markdown file into a new house-style spec in the store, deterministically, with no model in the loop; the convert-spec skill then runs an agent pass over the result.

The markdown is ordinary GFM: it renders on GitHub with no plugins. Structure that markdown cannot express (section ids that differ from their heading slug, task statuses outside done/todo, diagram identity) rides in YAML frontmatter and sparse HTML comments, both invisible in every renderer.

Import always creates a new spec. No import path writes over an existing one, so there is no clobber guard, no content hash, and no merge.

1 · Overview

A SpecForge spec exists only as a single self-contained HTML file in the global store (~/.specforge/specs/<id>/spec.html, lib/store-paths.mjs). Every consumer outside SpecForge reads markdown: GitHub renders it, agents in other harnesses read it, other repositories check it in, and a diff of an HTML spec is unreadable in review tools.

Two conversions are missing. Out: no way to take a spec to a surface that speaks markdown. In: lib/specforge-cli.mjs import copies an HTML file into the store unchanged, and the only route for a .md file is the convert-spec skill re-authoring it by hand, which produces a different document on every run and cannot run headless or in CI.

This spec adds a deterministic converter in both directions, exposes it on the CLI, the review UI, and the skills layer, and leaves the existing agent re-author as a second pass on top of the deterministic result rather than as the only mechanism.

2 · Requirements

Problem

A spec is unreadable outside SpecForge, and a markdown design doc cannot enter SpecForge without an agent rewriting it. The first blocks sharing a spec into any markdown-native surface. The second makes ingestion non-reproducible: the same input file produces a different spec on each run, so no test can assert what conversion does.

Product requirements

  • An exported .md renders correctly on GitHub with no extensions beyond GFM tables and task lists.
  • An exported .md carries the spec's diagrams as viewable images, not as dropped content.
  • Any .md file converts into a spec that opens in the review UI and passes lib/lint-spec.mjs.
  • Import creates a new spec and never modifies an existing spec's HTML, meta, or comment threads.
  • Export is reachable from the CLI, from the spec action menu in the review UI, and from a slash command.

Engineering requirements

  • Zero runtime dependencies. The package declares none (package.json, runtime-deps badge in README.md); the markdown parser, the HTML walker, and the zip writer are in-house and use only node: built-ins. jsdom stays a devDependency.
  • Node 18 or newer, ESM .mjs, matching the tolerant-regex parsing style of lib/spec.mjs.
  • The deterministic converter runs headless: no model call, no network, no daemon required. The agent pass is layered above it by the skill.
  • Structural round-trip: html → md → html' preserves section ids and order, heading text, plan task ids and statuses, table cell text, code block content and language, and diagram references.
  • Imported HTML is sanitized: <script>, <iframe>, <object>, <embed>, and on* attributes are stripped, because the review layer serves imported specs in the browser.

3 · Goals & non-goals

Goals

  • export-md emits GFM that passes a CommonMark + GFM parse and renders on GitHub.
  • import-md emits a spec whose lintSpec() blocking checks all pass, for every fixture in the corpus.
  • The round-trip fixture suite asserts structural equivalence on one spec of each doc type (design, research, design-impl, impl).
  • Both directions are unit-testable with node --test and require no browser.

Non-goals

  • Deck specs (templates/spec-base-deck.html). export-md on a deck exits non-zero with a message naming the limitation.
  • Updating an existing spec from a markdown file. Import creates a new spec; there is no --into.
  • Exporting comment threads. They live in comments.json and stay there.
  • Storing the generated .md in the spec directory. It is derived on demand.
  • Markdown as the authoring source of truth. The spec HTML remains the document; markdown is a projection and an entry point.
  • A published or tunnel-exposed markdown endpoint. The download route is local-daemon only (see Q1).

4 · Design

Summary

Four new library modules and one orchestration module, all under lib/. html-to-md.mjs walks spec HTML and returns markdown plus an asset list. md-parse.mjs turns markdown into a block AST covering the house subset. md-to-html.mjs turns that AST into section HTML and composes it into the per-type template shell. store-md.mjs is the only module the CLI, the daemon, and the skills call. zip.mjs writes a zip using node:zlib so the review UI can hand over a markdown file and its assets in one download.

Request flow

Export mechanics

  • Destination resolution: --out naming a directory writes <slug>.md into it; --out ending in .md writes that exact path; omitted --out writes into the current working directory. <slug> is the slugified spec title.
  • Assets: a spec with n inline <svg> elements produces <slug>.assets/ holding n files named <section-id>-<k>.svg, each a standalone SVG document with an xmlns attribute added. A spec with zero diagrams produces no directory.
  • Palette variables inside a lifted SVG (fill="var(--panel)") do not resolve in a standalone file. The exporter inlines the light-theme token values from the spec's [data-theme="light"] block as a :root style element in each written SVG.
  • --zip writes <slug>.zip containing the .md and the assets directory, and writes no loose files.
  • Nothing is written into ~/.specforge/specs/<id>/. A stored copy would go stale on the next spec edit and there is no invalidation hook to keep it honest.

Import mechanics

  • Frontmatter: a leading --- fenced block parsed as flat key: value pairs only. Nested maps, block scalars, and sequences are not parsed; they are reported as unsupported and ignored.
  • Type: --type wins; else frontmatter type; else general. The value is validated against SPEC_TYPES (lib/meta.mjs). A foreign markdown file has headings of its own and no house section set, so general is the shell that fits it; the prerequisite below added that type.
  • Title: --title wins; else frontmatter title; else the first # heading; else the file basename.
  • Sections: each ## opens a <section id="…" data-sf-section>. The id comes from an immediately preceding <!-- sf:section id="…" --> marker when present, else from the slugified heading text. Duplicate ids get a -2, -3 suffix, which keeps the unique-section-ids lint check green.
  • Content before the first ## becomes the tldr section. Headings deeper than ## stay inside the open section as h3 and h4.
  • Plan reconstruction: a section whose id is impl-plan has its ### stage headings and task-list items rebuilt into the data-sf-stage / data-sf-pr / data-sf-task / data-sf-status markup that parsePlan reads. A checked box maps to done, unchecked to todo; a <!-- sf:task … --> marker overrides both.
  • Tracker: task-tracker is regenerated by calling renderTrackerTable(computeTracker(html)) from lib/tracker.mjs after the plan is built. It is never parsed from the markdown.
  • Assets: an image link is resolved relative to the markdown file. An .svg target is inlined verbatim as <svg>. A raster target of 512 KB or less is inlined as a base64 data: URI; above 512 KB it is dropped and named in the report, because a spec must stay a single self-contained file.
  • Sanitization: passed-through raw HTML has <script>, <iframe>, <object>, <embed> elements and on* attributes removed before it enters the spec.
  • Shell: the type's template resolves through lib/store-templates.mjs. Its <section> elements are replaced by the imported ones; theme CSS, palette tokens, and the TOC container are kept, and TOC links are rebuilt from the imported sections in document order.
  • Provenance: meta.origin is the absolute path of the source file (the field cmdImport already sets). meta.derivedFrom is the frontmatter specforge_id when present.

5 · The dialect

SF-MD is GFM: CommonMark, plus tables and task lists, plus YAML frontmatter, plus HTML comments. Every construct in it renders on GitHub with no extension. Markers exist only where markdown has no way to carry identity, and are emitted only when needed.

Loss ledger

What a round trip does not preserve. Each entry is accepted, not a defect.

#Not preservedEffect on the re-imported spec
L1.tag span classes (good, bad, warn) inside prose and table cellsThe tag's text survives; its color does not. A cell reading "chosen" is plain text.
L2Inline style attributes and column widthsDropped. The template's default table and panel styling applies.
L3Table cells containing block content (lists, multiple paragraphs)Flattened to a single line with <br> separators, since GFM cells are inline-only.
L4Raster images above 512 KB referenced from an imported markdown fileDropped and named in the import report.
L5Prose whitespace and attribute orderDiffers. The round-trip assertion is structural, never byte equality.
L6Comment threads, block registry (blocks.json), share and publication stateNot exported and not carried into the new spec. The new spec starts with no threads.
L7<section> nestingNot applicable: specs do not nest sections (lib/spec.mjs header comment).

Parser subset

Supported blocks: ATX headings h1 to h4, paragraphs, fenced code (``` and ~~~) with an info string, GFM tables, unordered and ordered lists nested to three levels by two-space indent, task-list items, blockquotes, thematic breaks, images, HTML comments, and raw HTML blocks. Supported inline: **bold**, *emphasis*, `code`, [text](url), ![alt](src), and autolinks.

Not supported: setext headings, reference-style links, footnotes, definition lists, nested tables, and YAML beyond flat pairs. Each occurrence is recorded in report.unsupported with its line number and passed through as escaped text, so no content is lost silently and the agent pass has a list to work from.

6 · Testing

Test-infrastructure design only. The suite runs on node --test (package.json test script) with unit tests in test/ and a Playwright e2e in test-e2e/review.e2e.mjs. Existing tests already point SPECFORGE_HOME at a temporary store, which covers store isolation for both new paths.

  • Gap: there is no fixture corpus of spec HTML. Add test/fixtures/md/ holding one spec per doc type plus its expected .md golden file and expected asset names.
  • Gap: there is no way to assert two spec HTML documents are equivalent. Add test/helpers/structural-equivalence.mjs exporting assertStructurallyEquivalent(a, b), comparing section ids and order, heading text, plan task ids and statuses, table cell text, code block content and info string, and image references. It reports the first mismatch as a named field, not as a diff of the whole document.
  • Gap: the e2e harness drives the review page but never a download. Add a Playwright step that clicks the new menu row and asserts the response content type and filename.
  • No new environment, service, or credential is required. Both conversions are pure functions over strings and files.

#DecisionChoiceRationale
D1How much machine metadata may the markdown carry?YAML frontmatter plus HTML-comment markers, emitted only where markdown cannot carry identity.Both render as nothing in every markdown renderer, so the file stays readable while section ids and task statuses survive.
D2Where do inline SVG diagrams go?A sidecar <slug>.assets/ directory, referenced by a normal image link.GitHub's sanitizer strips inline SVG, so an inlined diagram would render as nothing. An image link renders everywhere.

8 · Open questions

  • Q1 · resolved Should /api/spec/:id/md be reachable through the publication gateway (lib/gateway.mjs, lib/publications.mjs), so a reviewer holding a share link can download the markdown? No, not in v1. The route is registered on the local daemon only and the gateway does not proxy it. A share token today grants a read-only review page; extending it to a full document download is a change in what sharing means, and no requirement in §2 asks for it. Adding it later is one proxy rule.
  • Q2 · resolved On a re-import of a file SpecForge exported (frontmatter carries specforge_id), what is the agent pass allowed to change? Structure and gaps, not prose. When report.unsupported is empty and the lint passes, the agent verifies and stops: no rewriting of sentences the deterministic pass restored. It rewrites only what the report names (unsupported constructs, dropped assets) or what the lint fails on. A foreign markdown file has no specforge_id, so it gets the full pass including register. This keeps the agent on every import (D6) without letting text drift on each cycle.

Design decisions (implementation time)

Choices made where the spec was ambiguous.

  • The section-id comparison strips the display ordinal. §5 said a marker is written when slug(heading) !== id. House headings are numbered, so slug("3 · Design") is 3-design and every section in every spec got a marker, which made the sparse-marker rule worth nothing. headingSlug() drops a leading ordinal before comparing.
  • The section marker sits under its heading, and names that section. The example in §5 showed it there; the importer first read it as belonging to the next heading, which shifted every id in the document by one. Caught by the round trip on its first run.
  • A section title is compared by text, not by heading level. Markdown gives a section exactly one heading, so the house TL;DR (an h4 inside a panel) necessarily returns as the section's h2. Recorded as loss L8; headings below the title are still compared exactly.
  • The tracker is exempt from round-trip content comparison. It is regenerated from the plan rather than read back, so its heading and rows are output of lib/tracker.mjs, not of the conversion. That it exists and holds its position is still asserted.
  • Diagram files are numbered within their section (architecture-1.svg, flow-1.svg), not across the document, so adding a diagram to one section does not renumber another's files.
  • isSafeUrl lives in lib/md-parse.mjs, the bottom of the import stack, because the inline renderer builds <a> and <img> straight from markdown link syntax and needs the same guard as the raw-HTML sanitizer. One definition, both paths.
  • data:image URIs are allowed, except svg+xml. An inline raster is how an image survives into a self-contained spec; SVG carries script and executes when navigated to.
  • Containment is checked on the real path. resolve() is lexical, so a symlink inside the source directory pointing anywhere passed. Both ends go through realpath, and the read uses the resolved path.
  • The zip stores rather than deflates when deflate would grow the entry, and carries a fixed DOS timestamp unless one is passed, so the same input produces the same bytes and a test can compare them.
  • Path safety is enforced at three levels, not one. The zip writer refuses an entry whose name has a .. segment, the exporter reduces a section id to a safe token before it becomes a file name, and the importer reduces a marker's id to what an HTML id may be. The entry name is assembled from the two layers above it, so guarding only the writer would have left the assembly free to produce something the writer then refused.
  • Consecutive inline nodes are gathered into one paragraph. House markup puts prose straight inside a .callout with an inline <code> in the middle; walking those children as separate blocks emitted the code as bare text. Found by exporting this spec and reading the warning.

Deviations

Intentional departures from the spec, and why.

  • The sanitizer allow-lists elements and attributes; §4 specified a block-list ("strips <script>, <iframe>, <object>, <embed>, and on* attributes"). Review found four bypasses of that block-list in four rounds, each a different spelling of one idea: a quoting form the pattern missed, an entity-encoded scheme, a solidus standing in for the separator between attributes. The list of dangerous things is a guess, and the guess is what gets enumerated. Allow-listing makes the class a non-event: an attribute nobody listed is dropped whatever it is called.
  • The import report field is assetsDropped, not assetsResolved. The interesting number is what did not make it, and each entry carries its reason.
  • Stage 3's e2e is a new file (test-e2e/download-md.e2e.mjs) rather than a step inside test-e2e/review.e2e.mjs. That file imports server/app.mjs and lib/paths.mjs, both deleted in the v2 retirement, so it cannot run; it is left alone rather than repaired as a side effect of this work.
  • The general spec type was built first, as Stage P. Not in the original plan: the importer had no shell to compose into that did not impose a section set the source document does not have.

Tradeoffs

Alternatives considered and why the chosen path won.

  • An in-house markdown parser against marked + turndown. The subset is bounded by what the house templates emit, and the package advertises zero runtime dependencies. Cost: roughly 350 lines to own, and two parser bugs the tests caught (an ordered list absorbed into a preceding bullet list; a footnote reported twice because it also matches the reference-link shape).
  • Structural equivalence against byte equality. Byte equality was never reachable: whitespace, attribute order, inline styles and tag classes are all documented losses. The assertion names the field that moved, which is what made four separate conversion bugs diagnosable in one line each.
  • Regex parsing against a DOM library. Kept, matching lib/spec.mjs. It cost two file-corrupting mistakes during development (raw control characters written into a source file, making it binary to grep) and one class of security bug that a real parser would not have had. A DOM would be a runtime dependency in a plugin that installs into a user's Claude Code.
  • Unwrapping unlisted elements against deleting them. Unwrapping keeps the author's text and discards only the markup. Deleting would be safer against an element whose content is the payload, which is why script, style and the framing elements are dropped whole instead.
